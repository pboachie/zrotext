# Candidate encrypted templates

Rust `template_crypto` and Go `EncryptedTemplateScope` implement ZTWT01 AES128-GCM HPKE templates using the existing native P-256/HKDF-SHA256 suite. Rust requires 1.99.1; Go requires 1.26.10. Dependencies and licenses are unchanged.

The caller supplies independent scope, a root-pinned verified profile02 manifest, and trusted comparison time. Scope includes account/device/line/interval/template identifiers, binding generation, revision, expiry, trust generation, manifest version, peer digest, reader identifier and manifest digest. The exact 222-byte scope encoding is authenticated as AAD and included in the HPKE info domain. The selected active role2 reader must have workflow scope8; an active role4 workflow signer with exact scope2 must match device and line. Expiry must be future and within thirty days. Comparison cannot precede the manifest's verified comparison.

`SealEncryptedTemplate` / `seal_encrypted_template` and software/protected opening equivalents are immutable-snapshot primitives. `SealCurrentEncryptedTemplate` / `seal_current_encrypted_template`, `OpenCurrentSoftwareEncryptedTemplate` / `open_current_software_encrypted_template`, and Windows protected equivalents additionally require a callback supplying independently current verified manifest and comparison. They call it before crypto and again before exposing ciphertext or plaintext. Both calls must authorize the exact scope under the same enrolled/current root; time cannot decrease. Failure suppresses the result. The decrypted owned buffer is cleared on all exits, and content is parsed only after the final check. Go immutable strings and runtime/provider internal copies cannot be reliably erased.

These callbacks do not authenticate HTTP responses or persist a high-water mark. The application supplies those guarantees. No owner transport, template storage/revision CAS, binding discovery, application credential, publication or live authority is implemented here. Current scope changes refuse; callers must explicitly choose a new scope rather than silently rebinding stored ciphertext.

Canonical template content must fit 1..32768 plaintext bytes, even though the independent local content API permits larger representations. Opening verifies exact expected AAD and framing, authenticates HPKE before parsing, and rejects noncanonical JSON or invalid UTF-8. Every seal uses fresh ephemeral randomness. Public CEK APIs continue to require exactly 32 plaintext bytes (48 ciphertext bytes); variable content support is private and cannot widen sealed-message CEK handling.

Protected opening takes the existing qualified Windows PCP recipient. It retains provider/export-policy/public-point qualification, locked native-handle lifetime and no software fallback. Sealing needs only the authorized public point and does not require custody of a signing key. `EncryptedTemplateDigest` / `encrypted_template_digest` hashes bounded transport bytes and provides no authority claim.

## Qualification

`test-template-crypto.py --producer PATH --binary PROBE` requires clean maintained source `26e876da9f34372d9cf26511993cf633971e0037` with its TypeScript SDK built. It opens maintained ciphertext, compares canonical plaintext, checks every envelope-byte mutation and genuinely encrypted malformed content, verifies authority failures before/after crypto, then independently opens two fresh native ciphertexts with maintained TypeScript. Native unit tests exercise variable-content bounds and prove public CEK width remains fixed with otherwise valid ciphertext.

Add `--hardware` on a qualified Windows host to create an exact owned recipient with a durable private receipt before creation. The producer receives only its public point and emits no selected private scalar. Cleanup deletes only that owned key, verifies reopening fails, and records deletion. The parent runner closes stdin and drains the child on exceptional setup failure; unresponsive cleanup retains the private receipt for investigation. Hosted CI executes software interop on Windows/Linux and does not infer hardware qualification. Clean installed-archive acceptance is a separate gate.
