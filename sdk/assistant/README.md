# Customer-local deterministic routine candidate

`CustomerRoutineService` calls the authenticated HTTPS routine service. Configuration holds the selected input credential, optional distinct output credential and, only for explicit owner actions, a live owner cookie and CSRF token. These are not model parameters. Requests are bounded, redirects are refused, and uncertain responses are never automatically retried.

`CustomerRoutineEngine` is disabled unless explicitly constructed with `enabled: true`. It uses the server's current policy and durable call admission, then reads the exact selected role-3 context through `WorkflowToolClient`. Existing verified-manifest ZTWC crypto decrypts this owner-declared context locally. Original inbound capture is not exposed by this service.

Five deterministic formats accept closed JSON: FAQ `{question, answer}` returns the owner-provided answer; intake `{fields: [{label, value}]}` returns at most sixteen selected fields; note `{note}`, reminder `{reminder}` and owner reply `{reply}` return their selected text. These routines do not run a hosted model, infer consent, interpret inbound events or send messages. Every generated action remains subject to exact authenticated owner review.

The assigned output context is the admitted call ID, revision one, on the unchanged selected interval, line and peer. Existing archive-reader HPKE seals output before `CipherArtifactStore` records it. The durable commitment is SHA-256 of the exact randomized archive ciphertext, never plaintext. The store bounds encrypted bytes and records immutable input revision/digest provenance. It is not a budget, consent or approval ledger. A replay with `execute_once: false` never regenerates output, including after an uncertain admission response.

After production, the owner separately decrypts and reviews the archive artifact, publishes those exact bytes through the existing owner context route, creates a role-3 projection with `projection`, and obtains a new exact output grant through `issueOutputGrant`. Grant issuance requires the actual owner password/MFA ceremony; the engine does not call it automatically. `bindAndResume` uses the fresh output credential plus independently current input credential. Input context and grant are not widened or replaced. Archive and role-3 ciphertexts differ; the owner declares the representation relationship because the server cannot prove plaintext equivalence.

The caller must supply independently verified current manifests, exact scopes and customer-held private keys; a response digest or a caller `verified` flag cannot replace them. Current service authority is checked again after decryption and sealing. Revocation, changed revision, expired policy, missing artifacts or unknown results stop the handoff. Window identity, timezone resolution, contact-purpose consent and owner action approval remain server authority.

Owned plaintext byte buffers are cleared on completion and refusal, including the sealing helper's internal copy. JavaScript strings, garbage-collected heaps, WebCrypto internals and operating-system copies cannot be guaranteed erased. SQLite deletion/pruning removes logical records; it does not guarantee physical erasure of database pages, WAL, backups or storage media. Retained artifacts are ciphertext. Customers must protect the local store directory and apply their own disk encryption and retention policy.

The service composition is a default-off candidate. Unit HTTPS fixtures use synthetic service policy; they do not prove PostgreSQL admission, deployment activation, physical-device behavior or carrier delivery. No package publishing or provider activation is performed.
