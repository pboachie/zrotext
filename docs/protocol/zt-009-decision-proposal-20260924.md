# ZT-009 decision proposal for sealed-content interoperability

**Local proposal, 2026-09-24. No accepted protocol or production crypto.** This is a decision candidate against [draft 01](zt-sealed-draft-01.md), its [decision log](zt-009-decision-log.md), and the merged sealed-inbound storage prerequisite. It does not change the draft 01 wire format or authorize clients to emit it. The accepted version needs its own profile revision, exact vectors, implementation evidence, and recorded decisions for Q1–Q11. Android API 31+ remains the selected sealed-mode floor; API 28–30 remain eligible for the SMS gateway only.

## Critical correction before freezing bytes

The draft manifest digest covers its ECDSA signature. For any valid P-256 signature `(r, s)`, `(r, n - s)` also verifies over the same unsigned bytes, where `n` is the P-256 group order. A party that sees a manifest can change the complete-byte digest without the owner key if both encodings are accepted. Even with low-`s` enforced, an authorized signer can issue distinct valid low-`s` signatures over identical fields. The [synthetic executable regression](../../crates/server/tests/zt_manifest_ecdsa_malleability.rs) shows both valid signatures and distinct complete-manifest digests. **Propose `manifest_identity_digest = SHA-256(manifest_without_signature)`** after exact parse and successful owner-root signature verification. Use this semantic digest in envelope `manifest_digest`, chain `previous_manifest_digest`, same-version fork checks, and root-transition references. Keep the exact signed bytes as evidence, but do not treat signature randomness as a new keyset. Same version with identical unsigned bytes and another valid signature is the same manifest; different unsigned digest is a fork. This mirrors the envelope's existing unsigned-byte idempotency digest.

Also propose canonical low-`s` signatures for both manifests and envelopes to keep their wire representations strict: signers convert `s` to `min(s, n-s)`; verifiers require `1 <= r < n` and `1 <= s <= floor(n/2)` before ECDSA verification. DER-to-raw conversion rejects nonminimal, negative, zero, overflow, extra and trailing encodings. Never normalize a received signature. The unsigned-digest choice solves stable manifest identity even when two valid low-`s` signatures differ; low-`s` alone does not. Both changes need a new profile revision and vectors. Any already-issued draft-01 chain or envelope digest needs explicit versioned migration or re-enrollment; silently rehashing stored manifests would corrupt references. Deterministic ECDSA as in [RFC 6979](https://www.rfc-editor.org/rfc/rfc6979.html) is useful for fixtures but cannot be assumed of Android Keystore or Web Crypto. Cross-client tests should verify a fixed fixture signature and accept independently generated canonical signatures, not require every signer to emit identical bytes. [Web Crypto ECDSA](https://www.w3.org/TR/webcrypto/#ecdsa) supplies fixed-width `r || s`; Android JCA supplies DER.

The other immediate gap is integration signing scope. Draft 01's two scope bits express send or inbound event signing, but do not express an integration's allowed line, recipient set, or reader permissions. A signing key with bit `0x0001` would be account-wide if the manifest is the only authorization source. Either explicitly accept account-wide outbound authority in the product contract, or add exact scope records in a new manifest profile. Do not imply line-scoped signing from an API token alone: a stolen or maliciously replaced relay could present a valid signed envelope to another device unless the device can verify the signer's line authorization from owner-signed bytes.

## Proposed decisions and closure evidence

|---|---|---|
| Q1 bootstrap | Generate the owner root in an owner-controlled client. The first trusted enrollment exports account ID, vault generation and full SHA-256 root fingerprint through a recovery card or direct device-to-device QR comparison. An SDK/phone pins these exact values only after the owner compares them through a channel distinct from the relay directory. A relay-served browser cannot, by itself, establish the stronger malicious-relay bootstrap claim because the relay can replace its JavaScript. | Specify the actual owner client and recovery-card UX. Test a substituted directory key, a swapped QR/account ID and a malicious served-browser update. | Q2 roles/scopes | Require exactly one active owner root record matching `root_public_point`; encryption roles have scope `0`, device auth has inbound-event bit only, integration signing has outbound-send bit only, and owner auth has no message-signing bit. | Q3 root rotation/reset | Define a separate, bounded transition object that signs the same exact transcript with both old and new roots: domain label, account ID, old/new generation, old semantic manifest digest, old/new root points, effective/expiry times. The old root signs continuity; the new root countersigns possession. Lost-all-root-and-recovery is a visibly new trust identity, never a silent continuation under account login. | Specify transition bytes, signature order and whether generation increases on routine root rotation. Test old-only, new-only, wrong-account, skipped, conflicting and expired transitions; drill recovery with and without the kit. Draft 01 has no such object, so root rotation is blocked. |

## Byte-level test matrix to publish before acceptance

1. Import [RFC 9180 Appendix A.3](https://www.rfc-editor.org/rfc/rfc9180.html#appendix-A.3) P-256 base-mode known answers unchanged, then publish ZT-specific `protected`, `body_aad`, each HPKE `info`/AAD, `enc`/`ct`, unsigned envelope, canonical signature and manifest bytes as hex. Include one outbound with device/archive/reader wraps and one inbound with archive/reader wraps.
2. Generate fixture-only deterministic CEK, nonce, HPKE ephemeral material and signing key. Keep fixture secret keys plainly marked test-only. For production paths, use fresh CSPRNG material and one HPKE Seal per context/wrap. [RFC 9180](https://www.rfc-editor.org/rfc/rfc9180.html) specifies suite IDs and KEM public-point validation; GCM nonce reuse must be excluded by key/nonce lifecycle.
3. Have TypeScript, Kotlin and Rust parse and verify the **same received bytes**, decrypt their authorized wrap/body, and reject every independently mutated field, malformed length/point/signature, role substitution, copied body under a new ID and high-`s` twin. Compare exact transcript bytes at every stage. Signing tests validate independent canonical signatures rather than assuming deterministic native signing.
4. Exercise manifest genesis, full chain, same-position fork, missing predecessor, expired/withheld update, root transition and local-store rollback. Separately test transport idempotency, server grant fences and radio one-attempt journal; cryptographic validity alone never authorizes a second SMS.
5. Perform a real supported-phone API 31+ Keystore/open test, recovery drill and relay canary sweep before changing any readiness status. These are evidence requirements, not claims satisfied by this proposal.

## Decisions still requiring product input

The owner-client bootstrap channel (Q1), integration signing scope granularity (Q2), root-transition semantics (Q3), tolerated revocation delay (Q4), six-segment UX/length disclosure (Q9), and recovery-kit lifecycle (Q10) are product/security decisions. The Android exact-profile Keystore path (Q5), signed binding-generation strategy (Q7), multipart/sequence semantics (Q8), and deployed leakage sweep (Q11) need engineering evidence. The candidate 24-hour window, seven-day inbound window and eight-day tombstone retention are proposed limits, not accepted policy. Until each row has an accepted choice and tests, ZT-009 remains open and sealed mode remains disabled.
