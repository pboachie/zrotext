# Candidate Android sealed preparation

The internal `Draft02OutboundPreparation` entry composes the candidate outbound
verifier, existing-key Android Keystore HPKE recipient, body authentication and
Room replay reservation. No service or stream handler calls it. There is no live
authenticated sealed-grant adapter or trusted-freshness provider. This is a
candidate integration, not available general messaging or an approved HPKE
production provider.

## Explicit local authority

The immutable local `Grant` binds account, message, attempt, device, line and line
generation; attempt generation, connection/deployment epochs and a process-local
session identity; origin hash, unsigned-envelope digest, manifest generation,
version and semantic digest; recipient digest, deadline and locally selected
subscription/card continuity. This type is not a device-stream frame. The caller
must obtain these facts independently of the received ciphertext. It cannot
translate a synthetic plaintext grant or manufacture one from a cached manifest.

`Current` is a defensive snapshot returned by a future authenticated adapter.
Null means unavailable. Each check requires the same grant, current verified
manifest context, exact reader set, positive nondecreasing trusted time, a live
deadline no more than 35 seconds away and conservative SIM continuity. Both the
input envelope and context arrays are owned before callbacks run. The existing
parser retains exact verified spans; body opening adds no parallel parser.

Ordinary wall time, a locally stored revision, BOOT_COUNT and elapsed time do not
establish trustworthy UTC. A future short-lived monotonic lease needs an
independently trusted initial checkpoint and must become unavailable after cold
load/reboot or suspected rollback. The compared-root store still returns
`NeedsFreshness` on cold load. This preparation code supplies no checkpoint or
rollback-resistance claim.

## Reservation and preparation

Room version 12 adds `sealed_preparations`, isolated from alpha attempts and
radio events. A transaction reserves the account/message and unique attempt
before any recipient-key lookup. Its immutable unsigned digest and grant digest
are metadata only. Identical duplicates, conflicting ciphertext, changed
signatures over the same unsigned identity and new attempts for the same message
cannot acquire another reservation. There is no cross-attempt retry policy.

The journal has a hard 1,024-row global capacity. Exhaustion fails closed. It has
no pruning, expiry or automatic recovery that could discard a replay fence.
Metadata is retained for the application database lifetime; database loss or a
privileged restored snapshot is not detected by this table. A future recovery
design must preserve these boundaries rather than silently clear the journal.

Only API 31+ existing, generated, non-exportable P-256 recipient keys reporting
TEE or StrongBox can enter preparation. Unsupported security levels return
`Unsupported`; a missing or changed key fails without creating a replacement.
The custom public-JCA HPKE composition remains a candidate. A successful unwrap
on a software-backed emulator is not successful hardware admission.

Body AES-256-GCM authenticates the exact received header/protected bytes. Strict
UTF-8 rejects empty or oversized bodies, malformed text, NUL and a leading BOM.
The selected subscription's `divideMessage` must produce one through six
nonempty segments that reproduce the exact text. It never calls an SMS send
method. CEK/plain byte buffers and owned mutable characters are cleared on all
failure paths; platform/JVM immutable Strings cannot be reliably erased.

Final line-generation/card-continuity checks and the `preparing` to `prepared`
CAS share a Room transaction. Context/time checks occur after transaction
acquisition, after mutation, after commit and before a one-use body handle is
consumed. Failed postcommit checks return no handle and retain non-resumable
metadata. Separate root/session state and Room are **not jointly atomic**.
`prepared` never freezes authority or substitutes for revalidation before a
future effect. A private, redacted closeable implementation owns transient text;
closing or consuming it clears the mutable buffer. It is not a radio token.

No body, peer, CEK or envelope is persisted. No alpha event, inbound window,
submit intent or radio-start record is created. Process death cannot reconstruct
a plaintext handle or resume sending from a journal row.

## Verification and remaining work

The pinned decryptable corpus is generated by
`android/test-fixtures/generate-sealed-preparation.mjs` using Node WebCrypto and
the SDK's existing `@hpke/core` dependency. Its public synthetic keys are test
material. Unlike signature-only vectors, it includes authenticated body opening
and independently signed AEAD/encoding negatives. The shared JVM/device corpus
also checks GSM, extension-table and Unicode six/seven-segment boundaries.

Room tests cover bounded capacity, two database instances, crash/reopen replay,
transaction waits, final-check rollback, write faults and v11 migration. Private
handoff tests use synthetic text to exercise postcommit failure and ownership;
they do not fabricate hardware admission. Selected emulator tests use fresh
temporary aliases, an independent test-only Tink sender and in-memory Room.
They report either actual platform-reported hardware admission or `Unsupported`
and require zero skipped tests. No SIM observation or carrier delivery is proved.

Live sealed grants/stream negotiation, trusted freshness acquisition, owner
comparison/recovery, provider/device acceptance and final intent/ack/effect
journal integration remain necessary. Radio execution and physical carrier/SIM
evidence remain separate release gates. No roadmap capability is completed by
this candidate alone.
