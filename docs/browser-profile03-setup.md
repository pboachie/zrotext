# Browser same-phone profile upgrade and recovery

The explicitly mounted owner conversation page offers a same-root profile03
setup controller. It composes the existing ordinary session/CSRF transport,
original registration and complete-v2 activation signature verifiers, existing
offline root proposal, original retained nonexportable SEALED approval key and
the actual phone's election signature. Pairing, root custody and original
complete-v2 phone installation must already have completed. Existing02 bytes,
routes and message-key purposes are unchanged.

Select the existing paired public signing point and independently compare its
fingerprint, account/root and previously accepted02 manifest checkpoint. The
controller verifies original signatures and the real returned checkpoint before
loading the exact original approval key. Missing retained custody refuses; this
flow never generates a replacement. The public upgrade proposal is downloaded
for the existing offline custodian. Returned signed03 output must match that
exact proposal before a fresh password/factor can reserve an opening.

After the paired phone signs, an explicit status/proof check verifies its
original raw64 low-S signature and the entire selected E500 scope. A separate
fresh password/factor approves the exact owner bundle with the originally
registered browser key. The browser persists that public bundle before sending
it. An accepted response is recorded separately from an independently checked
current profile; neither grants conversation content consent or message sending.

Public recovery uses a distinct IndexedDB store. Exact opening, reservation,
bundle and receipt slots are add-only, scoped to canonical origin, original
owner/account/device/line and independently compared checkpoint. Request success
is insufficient: publication waits for transaction completion. Competing tabs
cannot replace a retained slot; capacity is bounded to512 slots and nothing is
evicted automatically. Passwords, factors, private keys and recovery secrets are
not permitted in this store.

Find saved setup lists the matching original attempts without typing identifiers.
Load one and explicitly check its original status. A fresh sign-in by the same
original user can observe a historical attempt; it cannot approve old session
bytes. If an acceptance response was lost, the exact saved bundle and original
accepted server record are independently reverified without another signature,
factor or mutation. A valid503 is still UNKNOWN because a database commit may
already have succeeded. Only an explicit retry can submit the already retained
exact bundle, after current scope and proof checks; it never regenerates that
signature. Missing status is not evidence of nonacceptance.

Selection/CSRF/foreground changes, a regressing clock, expiry or close withdraw
live key leases and abort pending work. Public recovery and the retained key
survive closing the page. New attempts are explicit and preserve the server and
phone's permanent expired/closed/signed history; this browser does not infer a
safe reset from elapsed time.

The new controller/storage/page tests use actual SDK cryptographic verification,
genuine ephemeral synthetic signatures and the real nonextractable-key store
against simulated HTTP and IndexedDB. They do not prove actual database/MFA,
browser persistence, phone/hardware, carrier or production acceptance. The full
matched server/socket/Android/effect composition and release checks remain
required before operational enablement. The root secret and recovery kit never
enter this page.
