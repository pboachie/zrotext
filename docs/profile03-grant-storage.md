# One-use profile03 grant storage

Migration115 adds `conversation_profile03_grants`. Its narrow factory derives a
grant from the original114 reviewed admission, the installed113 interval, live
original owner/session, exact current manifest and physical selection, current
full device lease, reader mappings, recipient policy and actual usage reserve.
The authenticated segment ceiling remains required and equal to the signed
reviewed intent. SQL checks structure and persisted current state; genuine
authentication, original signatures and complete cryptographic ancestry remain
independent production adapter requirements.

The factory atomically claims the original queued message and initial unleased
job, records generation1, and creates one granted attempt, dispatch fence and
immutable grant row. A deferred check repeats the complete current selection and
deadline before commit. Missing or changed records roll back the whole claim.
Only this exact initial effect is writable. This migration does not authorize
submit, callbacks, timeout, an UNKNOWN reset or a retry through a legacy API.

There is one issued attempt for the lifetime of each reviewed message, including
after a later proved-no-submit result. Exact retries return its original receipt
without renewing time, lease, generation, quota or the stable account tuple.
An original receipt is history, never fresh effect permission. A new attempt ID
for the same message refuses. Expired and unproven work cannot be rearmed.

The nonpersonal grant identity survives message/content and attempt erasure until
actual account erasure. It duplicates no recipient, ciphertext, intent or
signature. Terminal content erasure remains coupled to original114 personal
proof erasure; unresolved granted, submitting and UNKNOWN liabilities refuse
retention, including deletion of its dispatch job. Existing billing foreign keys
remain intact. Losing personal originals
cannot reconstruct them, reset one-use uniqueness or readmit a reused message ID.

Both issue and fetch select root, exclusive account fence, actual stable anchor
and account row before original owner and device readers. An absent attempt may
select those transaction locks and return no row; it grants no owner/device
permission. Current grant reads require the exact unexpired granted attempt and
fence plus all original/current scope, and mutate nothing. The initial factories
support read committed transactions. Actual new grants version the anchor tuple
without changing the selection epoch, so stale repeatable-read and serializable
ordinary writers cannot revive an older view. Conflicting tuple/account lock
orders refuse promptly.

Original review expiry is checked at its retained admission time. Grant expiry
is instead bounded by the current original owner, interval, message, key/mapping
and full device lease deadlines, a held adapter deadline, and at most30 seconds
from the actual primary issue time. These boundaries are checked again after
waits. Owner sign-out, Stop, reconnect, root/manifest changes and mutable reader
mapping changes do not translate an old message into new permission.

A real unrefunded outbound reserve is required. Grant/fetch checks applicable
current payment risk, holds, reconciliation and invoice-bound grace without a
second debit or new-admission capacity test. A configured manual self-hosted
quota needs no hosted subscription. For an isolated hosted installation, NOWAIT
prelocks precede the qualified existing106 protected projection helper. Its
backend identity verification and pinned installation path are preserved. The
expiry of that exact verified backend session also caps the grant; reading it
does not create or renew a backend proof. The protected check repeats on each
current read, so replacing a proof cannot extend an already issued grant;
migration106 is unchanged. A retained reserve alone is not current permission
after a new payment hold.

After grant issuance, mandatory writers freeze both old and new ledger identities
for that message. Direct refunds, reassignment and deletion cannot release its
charged reserve. The original usage period retains a net reserved-unit floor
derived from its actual reserves and immutable grants; its counters cannot be
reset or decreased around that floor. Genuine reserves and refunds for other
messages in the same period remain available. Before issuing a new grant, the
current predicate also checks the already reserved candidate exactly once, so a
prior aggregate reset refuses without a second debit or a new capacity test.
This slice supplies no financial release authority for a granted or UNKNOWN
message; a future release needs separate typed evidence. Normal account erasure
keeps its existing lifecycle, and the one-attempt identity never rearms.

The ordinary runtime receives SELECT and only the narrow issue, lock and
readiness methods. Internal predicates and direct grant DML remain denied.
Closed function declarations, exact bodies, ownership, ACLs and the complete190
relation inventory reject partial or changed installations. The Rust
`conversation_profile03_grant_storage` module verifies this storage capability;
it is not an authentication, signature or radio witness. Grant03 and Fetch03
wire formats are unchanged. Actual producer/fetch mounting, phone effects and
integrated acceptance require separate implementation and qualification.
