# Browser message-key approval

The owner conversation page connects the existing nonexportable browser message
keystore, public same-root manifest proposal, exact install transport and
accepted-history controller. It derives account, original user, device, line and
root scope from the independently compared original setup and actual owner
session. It does not ask the user to type those fields again for this step.

After complete history is verified and its highwater committed, the owner
explicitly selects enrollment, renewal or replacement. An existing local key
remains unchanged. A new key requires separate retention consent and a committed
readback before its public proposal is available. Missing enrolled custody is
never regenerated as recovery. The existing offline custodian reviews the exact
public proposal; root material stays outside the page. Returned output must
match every proposed unsigned byte and the same-root policy before the retained
message key signs the distinct513-byte installation possession statement.

The exact public proposal, original possession bytes and a submission marker are
committed before their respective handoffs. The marker is committed and read
back before network mutation. No password, factor or private key enters that
recovery record. One current attempt occupies a bounded record per scope;
completed attempts may be superseded by a subsequent explicit proposal only
after actual accepted-history confirmation. An uncertain submission remains in
place and has no automatic retry. A definite refused response may enable an
explicit retry of the same original with new factors. An unsent original can
resume under its unchanged owner session and deadline without signing again.

An expired unsubmitted proposal can be superseded by an explicit fresh public
request using the same retained key and verified history. This is available only
when the committed submission marker is false and no receipt exists. A genuinely
service-checked, complete-history-confirmed approval whose local private key was
lost permits explicit replacement with new retention consent; it remains a
missing-key state until that new proposal is separately approved and accepted.
Neither recovery action clears a submitted uncertain attempt.

Fresh same-original-user sign-in can reconstruct the saved predecessor inside
the complete accepted chain and passively check an old attempt. History must
traverse both the existing durable highwater and this additional exact target,
including when either lies inside a page. The historical token and signed bytes
are exposed only after the full snapshot completes; they grant no present
permission. After a positive receipt, the page rechecks the exact accepted
successor and prefix through this same path and commits the updated highwater.
A locally saved receipt alone cannot produce the confirmed state.

Existing short signing, owner-session and offline-custodian windows remain.
Expired or changed-session unaccepted originals require explicit status and
fresh recovery; they are never rebound or silently renewed. Keeping the public
request does not extend these windows. Losing the original SEALED approval key
also remains distinct from replacing a browser message key.

Visibility, compared selection, origin, CSRF, sign-in, timeout and monotonic-clock
changes withdraw active work. Parent history guards are rechecked before and
after asynchronous key work even if an input changed without a DOM event.
Browser key approval is separate from a current phone physical handle,
foreground conversation consent, reviewed message admission, grant/fetch and
radio authority. The new owner-page source does not mount the server runtime or
enable messaging by itself.
