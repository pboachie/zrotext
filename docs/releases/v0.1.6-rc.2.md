ZROtext's second release candidate is for development and controlled pilot
evaluation. It does not open general SMS sending or establish a supported
production deployment.

These notes are frozen at `main` commit
`38e8e04894b9443d258687948da2e0b3601303df`. They describe every pull request
merged after [v0.1.6-rc.1] up to that commit. A pull request merged later is
not described here; if the tag is placed on a later commit, add it before
publishing.

## Included behavior

Changes since [v0.1.6-rc.1], grouped by area. The complete list of pull
requests is under [Pull requests in this candidate](#pull-requests-in-this-candidate).

**Security and authentication.**

- Verifying an email address requires the registrant's password (#427), and
  content-bearing owner `GET` requests require the CSRF header (#428).
- Owner sessions expire after 72 hours of inactivity, and API keys record
  their last use (#362). Socket renewals and status writes count as session
  checks (#520), and a request's owner-session validation is reused for one
  unlocked re-check (#519).
- Creating an API key requires the owner's current password (and an MFA code
  when enabled). New keys expire after 365 days by default, with an explicit
  and discouraged opt-in for a non-expiring key; keys issued before this
  candidate keep working. Signing out other sessions does not revoke API keys
  unless the request explicitly opts in (#430).
- Registration invite tokens carry a signed expiry: seven days by default,
  and the admin CLI can issue shorter ones (#338).
- Established device sockets are capped per account, with slots handed over
  on reconnect (#431). The device socket's pre-proof challenge is now a
  stateless HMAC value with no database row and no anonymous per-device
  budget (#449, migration 054).
- Abuse budgets: owner pairing creation per account (#419), a separate owner
  step-up factor budget (#422), a verified owner's own password-reset request
  budget (#426) and daily reset-email cap (#440), verified abuse-budget
  subjects with their own counters (#423), per-device budgets for inbound
  opt-out and opt-in events (#434), and prune retention derived from each
  limit's window (#305). The signed `STOP`/`START` reply target stays alive
  for the whole event window (#433).
- A browser that completed a sign-in gets a signed trusted-browser cookie,
  and reset requests from it, or from networks an operator lists in
  `RESET_TRUSTED_CIDRS`, spend a separate daily budget that an attacker who
  knows only the address cannot exhaust (#528, migration 055).
- Database connections accept libpq `verify-full`/`verify-ca` SSL modes with
  clear `DATABASE_URL` errors (#368). A non-local database host, including a
  host literally named `db`, requires `sslmode=require` or the explicit,
  warned `DATABASE_ALLOW_PLAINTEXT=true` opt-in (#372).

**Request handling.**

- Owner and API requests that carry a body are authenticated before the body
  is read (#441). Missing or invalid credentials get `401` (or `403` for a
  bad Origin or CSRF header) from the headers alone, even when the body is
  also malformed; that combination returned `400` before. A malformed body
  from an authenticated caller still gets the API error envelope as an HTTP
  400 (#371). Each account may have at most four authenticated body requests
  in flight per server process; a fifth concurrent one gets `429`.
- HTTP admission is split into route classes with independent permit pools:
  provider callbacks (16), device WebSocket upgrades (16), anonymous
  authentication and enrollment (32), and everything else (64) (#421).
  Health, readiness and version probes get their own pool of 8 (#441). A full
  pool answers `503` with `Retry-After: 1` and no longer starves other route
  classes. A request body must be fully received within ten seconds of
  admission, or the request fails with a bare HTTP `408`, which is also
  returned when a handler passes its 30-second deadline (#421).
- Readiness probes and unauthenticated requests do not take database pool
  connections (#370). Password-hash saturation answers HTTP 503 instead of
  queueing (#363), and Argon2 permit waiters are capped (#446). Worker-pool
  admission waits out an imminent socket release (#518), and a free permit
  waits briefly for a socket that is being reset before opening a new
  connection (#590). Device session leases renew at most once per half
  heartbeat interval (#420).

**Performance bundles.** Each bundle merged already-reviewed pull requests
unchanged; the member pull requests are closed, not merged on their own.

- Android client efficiency (#556: #535, #540, #542, #543, #546). The alpha
  evidence pump is event-driven instead of a 3-second journal poll,
  `device_status` has a 25-second floor on phone and server, the active
  subscription list is resolved once per status sample off the main thread,
  the WebSocket ping is removed in favor of the heartbeat and acknowledgment
  watchdog, and settled journal evidence is pruned from the phone after seven
  days.
- Database efficiency (#570: #533, #544, #534, #541, #536, #521, #562). A
  partial index keyed by account bounds the admission pending count
  (migration 052). Hot-path statements take one round trip, billed admission
  runs fewer statements, outbound accepts charge only their own account
  budget row, the inbound account lock is taken only for consent transitions,
  grant content is read once, and the webhook lane tick uses one probe
  statement. #572 fixed review follow-ups, including keeping an existing
  month's stored usage limit when an operator sets the policy limit to zero.
- Workers, mail and providers (#571: #530, #560, #565, #561). Provider-wide
  Stripe failures pause both billing queues with a capped backoff that
  honors a numeric `Retry-After`. Webhook, Stripe and SMTP workers hold a
  database socket only for database phases, never across network I/O, and
  producers wake the webhook lanes and the account-mail worker after commit.
- Owner dashboard efficiency (#555). The event stream backs off from 2 to 15
  seconds while idle, live reloads are rate-limited, a reconnect refreshes
  once, static assets are served with strong ETags and `304` answers, the
  Compose Caddy edge compresses text responses (not event streams),
  sign-in loads the visible lists first and a new `GET
  /v1/billing/device-capacity` returns only the capacity view, and SMS line
  activation polling slows when idle.
- Bounded owner queue counts use per-category partial indexes (#448,
  migration 049), the dispatch recent-grant probe is bounded (#522,
  migration 050), webhook delivery history pages backward per endpoint
  (#568, migration 057), abuse-counter charges update in place after an
  index is dropped (#566, migration 058), and owner erasure's foreign-key
  checks have support indexes (#554, migration 059).
- Maintenance pruning logs failures and drains bounded backlogs (#365),
  delivery recovery sweeps finish within each tick (#398), the webhook TLS
  verifier is built once per process (#311), and one unreadable webhook
  endpoint secret no longer blocks startup (#366).

**Owner dashboard, observers and erasure.**

- Device and message updates stream live to the dashboard (#401), with
  bounded per-device queue counts (#308). Dashboard blockers are explained in
  place and saved reports show their age (#340). A browser-only template
  preview is available (#323).
- Owners can invite device-status observers from `/owner/seats` (#457,
  migration 053, building on the observer memberships in #397 and migration
  048). Creating an invitation requires the owner's password (and MFA when
  enabled). The token is shown once, expires after seven days, works once,
  and is bound to the invited address. Observers see account-scoped device
  status only, never message content, device management, keys or billing.
- Owner account erasure (`POST /v1/owner/erasure`), first added in #320 and
  deferred in #384, is restored behind a locked authentication fence with an
  MFA step-up (#450). It is local and bounded: it deletes this server's rows
  only and does not cancel Stripe subscriptions or customers, touch external
  systems, or rewrite backups. #586 fixed erasure on databases with migration
  054 applied; before that fix, every erasure there rolled back with `503`.
- The owner data export scrubs and seals content instead of failing (#418),
  alpha message IDs are scoped to the calling account (#425), and SMS line
  IDs are account-private with never-activated lines capped at sixteen per
  account (#436).
- The roadmap records the per-device SIM, queue-depth and radio readiness
  work as complete (#447) and was refreshed through 2026-09-29 (#532).

**Billing and usage limits.**

- At most one Stripe Checkout session may be open per account (#429), and
  billing drain failures expose bounded test diagnostics (#389).
- Quota-only usage-limit plans exist and are disabled by default (#468,
  migration 056). An operator defines plans in `USAGE_LIMIT_PLANS` and turns
  them on with `USAGE_LIMITS_ENABLED=true`. Plans carry no price or payment
  data. With the flag off, admission behaves as before.

**Failover (disabled by default).**

- Independent-quorum automatic failover gained a decision module (#312),
  execution against the writer database with a durable controller journal
  (#383, migration 051), a durable per-member observation store (#439), and
  member reports formed from raw probe outcomes with a local reporting loop
  (#564). It stays disabled unless `FAILOVER_QUORUM_ENABLED=true`. No
  production probe source exists yet, so reporting rounds abstain and the
  executor only holds.
- A read-only go/no-go checker supports manual writer promotion (#453). Its
  `--writer-stopped` check requires fresh sender reports (#467).

**Sealed and Android groundwork (experimental, gated).**

- Sealed v1 message admission (`POST /v1/sealed/messages`) is mounted only
  when `SEALED_ADMISSION_ENABLED=true`; off, the default, leaves the route
  absent (#545). Acceptance stores exact envelope bytes and queues them
  toward the bound device. It is not carrier evidence or an execution grant,
  and sealed dispatch to devices is not implemented.
- Android sealed decryption is bound to a valid execution grant using a
  proposed `sealed_execution_grant` device-stream frame. No hub emits the
  frame, and the Android executor that consumes it is dormant (#575).
- Dormant manifest authority and envelope verification (#302, #309, #352,
  #326, #341), candidate sealed inbound and outbound queues (#375, #377,
  #380), root possession, backup, enrollment and codec work (#329, #335,
  #343, #376, #394, #347, #435), compared Android roots with freshness
  boundaries (#334), trust-store recovery from bad clocks (#298), MFA
  preservation across password recovery (#316), SDK draft-helper hardening
  (#400), encrypted SDK ciphertext exercised across PostgreSQL and Android
  (#385), and sealed Android attempts prepared without radio authorization
  (#353). The Q1-Q11 sealed-protocol decisions are verified against the tree
  (#464).
- The Rust receiver enforces the strict UTF-8 sealed body rules (1-32,768
  bytes, no BOM, no NUL, no Unicode normalization) with decryption over the
  exact received envelope transcript, checked across Rust, TypeScript and
  Android against one corpus (#525). Adversarial cross-client vectors fail
  closed across the server, TypeScript SDK and Android (#466).
- Dormant provider SMS attempts and verified Telnyx receipts are defined
  (#379); provider sending is not enabled.

**Android client and devices.**

- Devices report privacy-minimal preconditions (#317) and selected-subscription
  network service (#396). Gateway accessibility semantics and layout were
  improved and reviewed (#313, #359). The gateway setup detects an
  RCS-capable default messaging app (#465). The SMS line activation picker
  uses the device ID from the devices API (#524).
- A stage-one outbound MMS spike tool exists in debug builds only (#442).
  Release builds draw nothing and reject its grant frame, and no server
  issues that grant in this candidate, so the tool is inert.
- Test tooling: a no-radio physical-SIM line activation and continuity test
  (#297), SIM selection among several in hardware pilot tests (#437), the
  journal upgrade probe aligned with schema v11 (#350), and a preparation
  probe retry (#444). Documentation covers SMS line activation device checks
  and a recorded dual-eSIM activation decline (#463), and the RCS inbound
  mechanism and its limits (#567).
- Publishing a GitHub Release builds an unsigned Android candidate from the
  tagged source (#443); it is not a signed, installable release APK.

**Operations, documentation and CI.**

- Content-free device liveness-run totals and a report tool (#454).
- The public API v1 routes are documented in an OpenAPI contract (#445);
  provider route options, sender identities and registration regimes have
  their own guide (#459); every device compatibility-matrix entry links to a
  repeatable test run (#462); and a data-handling proposal for the optional
  managed AI service is recorded (#456).
- Release metadata covers all embedded owner assets (#348), and the source
  release candidate is recorded without advancing release maturity (#322).
- CI and build speed (#573): the Rust cache from #523 hits, the server image
  uses one pinned toolchain and a release profile, Android CI caches Gradle,
  superseded runs are cancelled, and the release APK is minified with R8.
  Jules pull-request reviews are opt-in (#529). Test reliability fixes: #331,
  #337, #354, #357, #395, #531.

## Upgrade and compatibility

For a fresh installation, use the tagged
[Compose guide](../../deploy/compose/README.md) and
[self-hosting documentation](../SELF-HOSTING.md).

For an existing source-snapshot installation, record its source commit,
applied migration level and image identity; take a protected backup and
rehearse restore first. Follow the [upgrade
sequence](../../deploy/compose/UPGRADE.md): stop the API writers, apply every
missing migration with this source's migrator, reprovision the runtime
database role and restart the selected source. Read intervening migration
maintenance requirements. Keep dispatch and experimental gates at their
reviewed settings.

### Migrations

Upgrading from v0.1.6-rc.1 (highest migration 040) applies migrations 041
through 059. Run them through this source's migrator, never by hand. The
migrations added after the previous version of these notes are:

| Migration | Pull request | What it does | How it runs |
|---|---|---|---|
| 051 `failover_controller_state` | #383 | One-row failover controller journal | Plain table, in the file's transaction |
| 052 `admission_pending_index` | #570 | Account-keyed pending-message index | Online (`CREATE INDEX CONCURRENTLY`) |
| 053 `observer_seat_invitations` | #457 | Observer invitation table | Plain table, in the file's transaction |
| 054 `stateless_device_challenges` | #449 | Drops `device_auth_challenges` | In the file's transaction; see below |
| 055 `trusted_browser_epoch` | #528 | Adds `users.trusted_browser_epoch` (default 0) | In the file's transaction |
| 056 `usage_limit_plans` | #468 | Plan assignment and audit tables | In the file's transaction |
| 057 `webhook_history_index` | #568 | Per-endpoint webhook history index | Online (`CREATE INDEX CONCURRENTLY`) |
| 058 `drop_abuse_counters_updated_index` | #566 | Drops `auth_abuse_counters_stale` | Online (`DROP INDEX CONCURRENTLY`) |
| 059 `erasure_fk_indexes` | #554 | Five foreign-key support indexes for erasure | Online (`CREATE INDEX CONCURRENTLY`) |

Migrations 049, 050, 052, 057 and 059 build their indexes online, and 058
drops its index online. The migrator runs these statements outside the
numbered file's transaction, and the numbered file then only validates the
result. No operator setting is needed. A concurrent build permits message
writes but may wait for older transactions, so let the migration finish
before starting API workers and monitor it with
`pg_stat_progress_create_index`. Rerunning after an interrupted build drops
and retries a matching invalid index; an index of the same name with a
different definition stops the migration without being replaced. After 058
is recorded, every later run refuses to proceed if that index is re-created.
See the [Compose guide](../../deploy/compose/README.md) and the
[upgrade guide](../../deploy/compose/UPGRADE.md) for these rules.

Migration 054 drops the `device_auth_challenges` table. An older binary
still writes that table, so after 054 every device handshake served by an
older API instance fails. Do not run mixed versions; going back after 054
means restoring the pre-upgrade backup. Owner erasure also referenced that
table until #586, which this candidate includes.

### Operators updating from v0.1.6-rc.1 should expect

- `DATABASE_URL` transport policy is enforced: use `sslmode=require` (or
  stronger) for non-local hosts, or set the explicit `DATABASE_ALLOW_PLAINTEXT`
  opt-in described in the Compose guide. The local Compose development stack
  already sets it.
- Signed-in owners are logged out after 72 hours without a request.
- Email verification and password-reset flows use new rate budgets; see the
  upgrade guide's behavior-change notes.
- API clients see authentication decided before request bodies are read
  (#441): bad credentials with a bad body now get `401` or `403` instead of
  `400`, a fifth concurrent authenticated body request from one account gets
  `429`, and a body that arrives more than ten seconds after admission gets
  `408`. Authenticated callers with a malformed body still get the JSON error
  envelope, and admission limits are per route class, with a separate pool of
  8 for health, readiness and version probes.
- API-key issuance requires password step-up (plus MFA when enabled), new
  keys default to a 365-day lifetime unless a non-expiring key is explicitly
  requested, and signing out other sessions leaves API keys in place unless
  the request opts into revoking them.
- Invite tokens issued by rc.1 stop being accepted once the API runs this
  candidate; re-issue outstanding invites with the admin CLI.
- An account may hold at most sixteen never-activated SMS lines (#436).
- Password reset requests from a browser that signed in before, or from a
  network in `RESET_TRUSTED_CIDRS`, use a separate trusted daily budget. Both
  `RESET_TRUSTED_CIDRS` and `TRUSTED_PROXY_CIDRS` are empty by default. Set
  `TRUSTED_PROXY_CIDRS` only to the networks your reverse proxies connect
  from; `X-Forwarded-For` is ignored from any other peer. The
  `__Host-zrotext_trusted_browser` cookie lasts 90 days and is invalidated by
  a password change, a reset, revoking other sessions, an MFA change or
  erasure.
- Device socket challenges are stateless and valid for 60 seconds with 10
  seconds of clock-skew tolerance, so keep API instance clocks synchronized.
- Owner account erasure is available to owners (#450). It does not cancel
  Stripe subscriptions or customers.
- These stay off unless explicitly set: `SEALED_ADMISSION_ENABLED` (sealed v1
  admission), `USAGE_LIMITS_ENABLED` with `USAGE_LIMIT_PLANS` (usage-limit
  plans; setting only one of them stops startup), and
  `FAILOVER_QUORUM_ENABLED` (independent-quorum failover; when enabled,
  `FAILOVER_QUORUM_STORE_DIR` is required and must be an absolute path
  without `.` or `..` components). `SMS_LINE_ACTIVATION_ENABLED` also stays
  off by default.
- The MMS spike tool is in debug Android builds only and does nothing
  without a server-issued grant, which no server in this candidate issues.

The device stream remains protocol v1. The sealed-content profiles and SDK
are experimental. Upgrading does not authorize enabling SMS line activation,
sealed admission, usage limits, failover or other gated features.

image workflow passed, a verified Linux amd64 server image. The Android
source sets `versionName` 0.1.6-rc.2 and `versionCode` 8.

This release does not establish carrier delivery, different-card SIM swap
acceptance, broad OEM/network compatibility, hosted deployment readiness,
general unsolicited content capture, managed AI (data-handling proposal only),
provider sending, or general MMS sending. An emulator or a no-radio
physical-device test does not establish those outcomes. Physical-SIM
continuity and end-to-end opt-out evidence remain pilot validation work with
no recorded physical-device acceptance for this candidate. Independent-quorum
failover remains disabled by default and its promotion tooling is read-only.

builds only an unsigned Android candidate from the tagged source.
