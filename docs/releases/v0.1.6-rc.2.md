ZROtext's second release candidate is for development and controlled pilot
evaluation. It does not open general SMS sending or establish a supported
production deployment.

## Included behavior

Changes since [v0.1.6-rc.1], grouped by operator impact:

**Owner and API authentication hardening.**

- Verifying an email address now requires the registrant's password (#427).
- Content-bearing owner `GET` requests require the CSRF header (#428).
- Established device sockets are capped per account, with slots handed over on
  reconnect (#431).
- Verified owners get their own daily password-reset email budget, and the
  step-up factor budget is separated from sign-in completion (#422, #426).
- Verified abuse-budget subjects get their own counters (#403, #423), inbound
  opt-out and opt-in events get per-device budgets (#434), owner pairing
  creation is budgeted per account (#419), and the signed `STOP`/`START`
  reply target stays alive for the whole event window (#433).
- Owner sessions expire after 72 hours of inactivity, and API keys record
  their last use.
- Registration invite tokens expire after a bounded lifetime (seven days by
  default; the admin CLI can issue shorter ones).

**Request handling.**

- Owner and API requests are authenticated before their bodies are read, and
  rejected JSON bodies return the API error envelope as an HTTP 400.
- HTTP admission is split into route classes with independent permit pools —
  provider callbacks (16), device WebSocket upgrades (16), anonymous
  authentication and enrollment (32), and everything else (64) — and a request
  body must be fully received within ten seconds of admission (#421). A full
  pool no longer starves unrelated route classes.
- Readiness probes and unauthenticated requests do not consume database pool
  connections, and password-hash saturation answers HTTP 503 instead of
  queueing.

**Owner dashboard and API.**

- Device and message updates stream live to the dashboard instead of relying
  on snapshots, with bounded per-device `pending_messages` and
  `in_flight_messages` counts capped at 1,000.
- Devices report privacy-minimal preconditions (selected SIM, SMS permission,
  airplane mode, selected-subscription network service), dashboard blockers
  are explained in place, and saved reports show their age.
- The owner data export scrubs and seals content instead of failing, alpha
  message IDs are scoped to the calling account (#425), and SMS line IDs are
  account-private with unactivated lines kept bound (#436).
- Offline owner backup and recovery-verification commands exist with strict
  recovery-token and public root-card formats.

**Data handling and lifecycle.**

- At most one Stripe Checkout session may be open per account (#429).
- Database connections accept libpq `verify-full`/`verify-ca` SSL modes with
  clear `DATABASE_URL` errors; a non-local database host (including a host
  literally named `db`) requires `sslmode=require` or the explicit, warned
  `DATABASE_ALLOW_PLAINTEXT=true` opt-in.
- Maintenance pruning logs failures and drains bounded backlogs, delivery
  recovery sweeps complete within each tick, the webhook TLS verifier is
  built once per process, and one unreadable webhook endpoint secret no
  longer blocks startup.
- Operations tooling: a read-only go/no-go checker for manual writer
  promotion (`deploy/compose/promotion_check.py`, see the writer-promotion
  guide) and content-free device liveness-run totals with a report tool
  (`scripts/liveness_report.py`, see the Android testing guide).

**Sealed and Android groundwork (experimental, gated).**

- Dormant manifest authority, candidate sealed inbound/outbound queues,
  compared-root storage with freshness boundaries, and sealed Android
  attempts prepared without radio authorization (#353).
- Pure root-material codecs with server API compatibility, candidate
  generation-one root backup, MFA preservation across owner password
  recovery, and the draft-02 trust store recovering from bad clocks.
- Publishing a GitHub Release builds an unsigned Android candidate from the
  tagged source; it is not a signed, installable release APK.

## Upgrade and compatibility

For a fresh installation, use the tagged
[Compose guide](../../deploy/compose/README.md) and
[self-hosting documentation](../SELF-HOSTING.md).

For an existing source-snapshot installation, record its source commit,
applied migration level and image identity; take a protected backup and
rehearse restore first. Follow the [upgrade
sequence](../../deploy/compose/UPGRADE.md): stop the API writers, apply every
missing migration with this source's migrator, reprovision the runtime
database role and restart the selected source. Read intervening migration
maintenance requirements. Keep dispatch and experimental gates at their
reviewed settings.

Operators updating from v0.1.6-rc.1 should additionally expect:

- `DATABASE_URL` transport policy is now enforced: use `sslmode=require` (or
  stronger) for non-local hosts, or set the explicit `DATABASE_ALLOW_PLAINTEXT`
  opt-in described in the Compose guide. The local Compose development stack
  already sets it.
- Signed-in owners are logged out after 72 hours without a request.
- Email verification and password-reset flows interact with new rate budgets;
  see the upgrade guide's behavior-change notes.
- API clients see authentication decided before request bodies are read,
  a JSON error envelope for malformed bodies, and class-scoped admission
  limits with a ten-second body deadline.
- Existing invite tokens issued before this candidate expire under the new
  bounded lifetime.

The device stream remains protocol v1. The sealed-content profiles and SDK
are experimental, and live sealed message routes are not exposed. Upgrading
does not authorize enabling SMS line activation or other gated features.

This release does not establish carrier delivery, different-card SIM swap
acceptance, broad OEM/network compatibility, hosted deployment readiness,
general unsolicited content capture, managed AI (data-handling proposal only),
provider sending, or general MMS sending. An emulator or a no-radio
physical-device test does not establish those outcomes. Physical-SIM
continuity and end-to-end opt-out evidence remain pilot validation work with
no recorded physical-device acceptance for this candidate. Independent-quorum
failover remains disabled by default and its promotion tooling is read-only.
A signed Android APK is a separate founder-controlled step; this candidate
builds only an unsigned Android candidate from the tagged source.

See [release verification](../RELEASING.md) and
[device compatibility](../DEVICE-COMPATIBILITY.md) before using candidate
artifacts.
