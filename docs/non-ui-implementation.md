# Non-UI implementation ownership and acceptance

This is the implementation map for [#622](https://github.com/pboachie/zrotext/issues/622), read alongside the [roadmap](ROADMAP.md), [product plan](PRODUCT-PLAN.md) and authoritative [sealed decision log](../protocol/drafts/zt-009-decision-log.md). It records source boundaries, owning implementation lanes and remaining acceptance. It does not enable a feature, approve a protocol, close an issue or advance a release stage. Presentation and integrated visual acceptance remain in #605–#612.

The source baseline contains migrations through `079_workflow_integration_authority.sql`. Implementation lanes below retain their actual caller boundaries: a library or reviewable source candidate is not an enabled caller or an acceptance result. A helper or contract is not completion of its parent capability. When an owning lane changes, reconcile the actual caller, dependencies and tests before updating this map; a matching issue number alone is insufficient.

## How to read the boundaries

- **Mounted, default-off:** the shipping server has a configuration-controlled caller; the default leaves the capability unavailable. Its isolated tests do not authorize activation.
- **Library-only:** callable implementation and tests exist, but the shipping entry point does not opt in or mount the router.
- **Contract only:** specification, vectors or pure model exist; no external-effect implementation is implied.
- **Open source candidate:** the named PR owns the implementation; combined exact-head checks and integration may remain incomplete.

Owners below are the existing issue/PR implementation lanes, not additional competing assignments. General messaging waits for the [general-send gates](SMS-COMPLIANCE.md#gate-for-general-sending), current line/reader authority and controlled physical-device acceptance. Another restricted presentation candidate may retain these capabilities off with truthful limitations. Optional provider sending, managed AI and later billing/workflows are separate backlog; they are not automatic prerequisites for that restricted candidate.

## Shared service order and acceptance handoff

Root custody/profile/key decisions (#623–#625) and exact-action binding (#635) come first. Negotiated hub dispatch, lifecycle and phone caller integration (#626–#629) plus downgrade/leakage checks (#632) close the relevant messaging gates together. #630/#631 project the existing scoped resources; they do not create sending authority.

Contacts/purpose consent (#634), encrypted context (#636) and template persistence (#637) can progress against agreed contracts. Exact owner decisions (#638) precede approved scheduling (#639). Connector lifecycle (#640) precedes integration runtime (#641); existing agent adapters #614–#621 consume that shared runtime instead of reimplementing decision, checkpoint or queue authority. Customer-local routines (#642) remain bounded proposals until real shared services and messaging acceptance are available. Optional provider/AI/live billing/failover effects retain their separate gates.

For each remaining gate, retain the existing owning PR or issue, exact caller scope, current-source verification command and missing acceptance in its PR. A contract slice, `Prepared` metadata, successful browser fixture or emulator key test must not be described as an enabled end-to-end capability. Physical tests, candidate bundle rehearsal, actual-site promotion and hosted support/payment readiness are private operational work; this public map contains no infrastructure, credentials, customer data, raw captures or private business policy.

This map describes source boundaries only. It does not advance roadmap stages, general-send gate checkboxes, planned customer-catalog availability or production feature defaults.
