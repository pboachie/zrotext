# Jules reviews

Jules reviews are opt-in. A session starts only when the owner comments an explicit command on its own line at the start of a comment on an eligible same-repository PR: `/jules review` for a fresh review, `/jules address` for a focused comment-fix session, or the `@jules review` / `@jules address` aliases. Opening a PR, marking it ready, or submitting a review no longer starts anything, and Dependabot PRs are no longer reviewed automatically (the owner can still request a review by command). The Actions workflow polls labelled PRs for results and posts a generic advisory completion notice from `github-actions[bot]` with a link to the Jules session. Detailed reports and address summaries remain in Jules for maintainer review; they are not copied into public comments, reviews, artifacts, or logs. It never approves or merges a PR, and Jules does not publish comment fixes automatically.

A `/jules address` session receives only two kinds of feedback: Jules' latest validated review of the PR, retrieved from the session identified by this workflow's completion notice (or from a legacy review), and comments, inline comments and reviews whose GitHub author association is owner, member or collaborator. Comments from other accounts, including other bots, are left out, and text that claims to come from Jules or a maintainer does not change that; only the author identity recorded by GitHub counts. The workflow skips comment and review events from other accounts before the job receives the API key.

The integration runs from the trusted `main` workflow. It does not check out PR code in Actions. The API key is stored in the repository's `JULES_API_KEY` Actions secret and is sent only to Jules over HTTPS. Workflow dispatch with a PR number and mode is also available to repository maintainers.

Before starting a session, the workflow lists Jules sources, selects the single connected source whose GitHub owner and repository match this project, and checks that Jules has indexed the PR branch. A missing or ambiguous source fails closed; an unindexed branch defers the review. API failures report only a bounded status category, never the provider's message or request headers.

Jules limits how many tasks an account can run at once and per day; the base plan allows three concurrent and fifteen daily tasks. When Jules refuses a new session because of a task limit (`FAILED_PRECONDITION` or `RESOURCE_EXHAUSTED` when the session is created), the workflow defers the request instead of failing the check. A deferred review is not started by the schedule; the owner repeats `/jules review` after running sessions finish. A deferred `/jules address` is not retried automatically; the workflow comments on the PR, and the owner can repeat the command after running sessions finish. Frequent deferrals mean the Jules plan is too small for the repository's PR volume.

Reviews are limited to branches in this repository. For a stacked PR, Jules reviews the change against that PR's base commit rather than all parent changes. A review is marked stale if the PR head or its base commit changes while Jules is working. The schedule avoids repeated sessions for the same head when its base changes; request a new review after updating the parent branch. Treat Jules findings as a second opinion alongside CI and maintainer review.

## Pending-label collection

When a session starts, the workflow adds the `jules-pending` label to the PR. The label means "this PR still has an unfinished session", and the collector removes it exactly when no unfinished session remains - a still-running second session keeps the label, and results count whether they were published as issue comments or as PR reviews. Because the collector itself applies that rule on every visit, it also self-heals a stale label whose sessions all finished elsewhere. The removal is race-safe: an owner-command run can start a session while the collector runs, so the collector re-checks for unfinished sessions immediately before and after removing the label and restores it if one appeared. Non-PR issues that somehow carry the label are skipped, since they have no PR reviews endpoint. The scheduled collector lists only labelled open PRs in a single query and exits immediately when there are none, so an idle repository costs one listing call per run. Sessions that were already in flight when the label was introduced are labelled once by a maintainer dispatching the workflow with `backfill=true`; that scan counts results published as comments and as PR reviews, so an already-finished PR is not labelled.

## Completion and stalled sessions

Review prompts require an unattended, read-only review and a final JSON report with verified head/base commits, actionable findings (severity, path, line, evidence, and a feasible fix), actual test outcomes, and limitations. They explicitly prohibit asking permission to finish, speculative findings, and claims of tests that were not run. Session creation explicitly disables plan approval; it does not enable automatic PR publication.

On each scheduled poll, a review in `AWAITING_USER_FEEDBACK` receives at most one automatic message restating the review task and output contract, provided the PR is still eligible and its commits match. This also applies to existing sessions recorded by older start markers. A bot comment reserves the attempt before the message is sent, so an uncertain API failure cannot cause repeated replies; inspect the linked session manually if the attempt fails or Jules remains blocked. The workflow continues polling for completion. Address sessions, paused sessions, and sessions awaiting plan approval receive a single attention notice instead of automatic authorization. Changed commits produce a stale result without continuing the session.

A completed review receives a generic advisory GitHub PR review only if its final report passes the contract checks and matches the recorded commits. The notice does not state whether findings are empty or repeat model-supplied tests or limitations. Maintainers inspect the report in Jules and explicitly choose any generic outcome suitable for public sharing. Empty findings in the session report must be explicit. Blocked, stale, missing, oversized, or malformed reports produce an incomplete-result conversation comment, never a clean review. Older completed sessions with prose-only output also require a new `/jules review` request. Activity pagination must finish successfully and the latest timestamped agent message is selected; reports are not silently truncated. Scheduled collectors are serialized to avoid duplicate follow-ups.

These checks validate report structure and commit identity, not whether Jules' conclusions or claimed test results are true. Maintainer review and CI remain necessary. Jules session states and the follow-up endpoint are documented in the [Jules Sessions API](https://jules.google/docs/api/reference/sessions).
