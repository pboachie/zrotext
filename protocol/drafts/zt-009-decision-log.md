# ZT-009 candidate decisions and review gates

**Open decision log, 2026-09-23; decisions recorded 2026-09-26 below.** This records proposed wire rules and the decisions needed before the sealed profile can be accepted. No row approves production cryptography. Record the selected choice, alternatives, owner, decision date, and verification evidence in a future revision. A blank acceptance field keeps the gate open.

The companion [draft 01 byte profile](zt-sealed-draft-01.md) is the exact candidate under discussion. [RFC 9180](https://www.rfc-editor.org/rfc/rfc9180.html#section-7) defines the HPKE P-256 suite identifiers and 65-byte `enc`; [RFC 9180 §7.1.4](https://www.rfc-editor.org/rfc/rfc9180.html#section-7.1.4) requires validation of P-256 public-key inputs. [Web Crypto ECDSA](https://www.w3.org/TR/webcrypto/#ecdsa) specifies fixed-width `r || s` output and hashes the supplied message. These sources specify primitives, not this application's authorization or recovery policy.

A separate [profile-02 manifest and authorization candidate](zt-sealed-draft-02-manifest-candidate.md) specifies bounded bytes and local tests for Q1–Q4 and Q6–Q7. It proposes the unsigned semantic manifest digest and strict low-`s` signature rule identified in the [decision proposal](zt-009-decision-proposal.md). It is not an accepted decision or a production trust source; the acceptance cells below remain open.

## Q5 virtual feasibility observation (2026-09-23)

Two isolated Pixel 8 API 36 emulator tests passed. An Android Keystore P-256 key returned no private encoding and completed provider ECDH. Separately, Tink Java 1.23.0 with a `NO_PREFIX` P-256 HPKE key emitted a 65-byte encapsulated point followed by ciphertext and tag; matching `contextInfo` opened it and changed `contextInfo` failed. These tests did not combine the Keystore key with HPKE decapsulation or test nonempty HPKE AAD.

The ordinary Tink [HPKE decryptor](https://github.com/tink-crypto/tink-java/blob/v1.23.0/src/main/java/com/google/crypto/tink/hybrid/internal/HpkeDecrypt.java) consumes raw private-key bytes. The draft wrap requires a distinct nonempty AAD, so this library path does not yet satisfy the candidate profile. Q5 stays open pending a maintained compatible production path and exact cross-client vectors. No custom ECDH/HPKE bridge was accepted for production.

An isolated [instrumentation proof](../../android/app/src/androidTest/java/org/zrotext/gateway/KeystoreHpkeProofDeviceTest.kt) shows a narrower technical possibility. On a Pixel 8 API 36 emulator, an Android Keystore `PURPOSE_AGREE_KEY` P-256 private key returned no encoding, performed provider ECDH, and opened one draft-shaped 32-byte CEK wrap with distinct nonempty RFC 9180 `info` and AAD. The test-only composition separately opened the [RFC 9180 Appendix A.3.1](https://www.rfc-editor.org/rfc/rfc9180.html#appendix-A.3.1) known answer and rejected changed `info`, AAD, role, wrong key, invalid point, and malformed lengths. The command was `adb -s emulator-5554 shell am instrument -w -e class org.zrotext.gateway.KeystoreHpkeProofDeviceTest org.zrotext.gateway.test/androidx.test.runner.AndroidJUnitRunner`; result: `OK (3 tests)`. This code is outside the app's main source and is not a reviewed HPKE provider or production sealed-content path. The AVD run alone was not physical security-level evidence, and no real API 28–30 device testing was done. Q5 remains open.

The same three isolated tests passed on a dedicated Samsung SM-S928U running Android 16/API 36, build `BP4A.251205.006` (`OK (3 tests)`). For the temporary generated P-256 key, Android `KeyInfo` reported `TRUSTED_ENVIRONMENT` security level and the test confirmed no private-key encoding, successful Keystore ECDH/HPKE open, and deletion of the temporary alias. [Android's `KeyInfo` contract](https://developer.android.com/reference/android/security/keystore/KeyInfo#getSecurityLevel()) describes that reported level, but this run did not independently attest the hardware, test persistence across reboot/key loss, or integrate a maintained production HPKE provider. Q5 remains open.

A follow-up [provider study](zt-009-android-provider-study.md) records why the evaluated Tink, Bouncy Castle, and native Android HPKE APIs do not directly meet the Keystore plus nonempty-AAD requirement. Its emulator-only `@hpke/core` sender sealed a draft wrap to a newly generated Android Keystore key and the test-only Android receiver opened it with independently reconstructed `info` and AAD. This is cross-client wrap interoperability evidence, not a selected production provider or a complete signed-envelope flow. Q5 remains open.

A further API 36 Pixel AVD test passed a complete draft-01 outbound envelope from the pinned fixture through a bounded Android **test-only** parser, Keystore HPKE device-wrap opening, and body AEAD opening. A host-side `@hpke/core` sender created the device wrap with exact nonempty `info` and AAD. Gradle/JVM and the seven TypeScript vector tests passed; the host harness printed `PASS` and the instrumented class `OK (7 tests)`. Android did not verify the origin signature, manifest, grant or replay state in that initial proof; it had no production call path. This added interoperability evidence without accepting a provider or closing Q5.

A later local-only Q6 proof adds a dormant Android P-256 signature primitive for the exact received draft-01 outbound transcript. It checks the pinned signer's draft key ID, strict 64-byte Web Crypto `r || s` scalar ranges, explicit high-`s` policy, minimal DER conversion for Android JCA, and `SHA256withECDSA` over the label, length and original unsigned bytes. The browser fixture's valid high-`s` signature verifies only when the explicit interoperability policy permits it; its equivalent low-`s` form verifies under the strict option. Changed signed bytes, signer ID, signature and scalar bounds fail. The test-only receiver uses a pinned public fixture point before decryption, but no trusted manifest enrollment, role/scope, grant or replay validation exists. This is cryptographic feasibility evidence, not acceptance of a high/low-`s` policy or production signer authority. Q6 remains open.

**Q6 engineering recommendation:** a future versioned sealed profile should require low-`s` P-256 signatures on the wire. Browser [Web Crypto ECDSA](https://www.w3.org/TR/WebCryptoAPI/#ecdsa) emits fixed-width `r || s`; replacing a valid high `s` with `n − s` preserves verification and needs no second private-key operation. Android's [SHA256withECDSA provider](https://developer.android.com/reference/java/security/Signature) uses DER signatures, so sender code must reject nonminimal/negative/out-of-range DER integers and convert to fixed-width low-`s` raw bytes. Receivers then reject high-`s` aliases. The local helper and JVM/browser tests demonstrate conversion and equivalent verification. The current pinned draft-01 outbound signature is high-`s`, so enforcing this rule now would reject an existing vector and change the wire contract. Draft 01 remains unchanged; adoption needs a new profile revision, regenerated vectors, Android Keystore signer and Rust cross-client tests. No Q6 acceptance or production route follows from this recommendation.

On the rebased local branch, the focused Android/JVM build passed, the signature primitive's four JVM tests and eight TypeScript vector tests passed, and the API 36 Pixel AVD `@hpke/core` envelope-open harness printed `PASS`. A separate emulator test generated a temporary non-exportable Android Keystore P-256 signing key, converted its JCA DER signature to canonical low-`s` raw bytes, and verified the exact draft transcript (`OK (1 test)`, `m2_keystore_der_low_s=PASSED`). It removed the temporary key and debug/test APKs. These are virtual, test-only results; a supported-phone signer and trusted manifest/replay boundary remain untested.

The documented Android Keystore ECDH purpose, [`PURPOSE_AGREE_KEY`](https://developer.android.com/reference/android/security/keystore/KeyProperties#PURPOSE_AGREE_KEY), was added in API 31. The current gateway package has `minSdk` 28, so this non-exportable ECDH route cannot be assumed across its stated device range. A software HPKE key encrypted at rest under a [Keystore AEAD key](https://github.com/tink-crypto/tink-java/blob/v1.23.0/src/main/java/com/google/crypto/tink/integration/android/AndroidKeystore.java) would have a different exposure claim because its private bytes enter app memory for decryption. The product decision below excludes API 28–30 from sealed mode; the exact nonempty-AAD HPKE provider and key lifecycle remain open engineering work.

The [Android provider study](zt-009-android-provider-study.md) adds a dormant
API 31+ payload-key boundary with enrollment-only generation, existing-key-only
ECDH and exact P-256/key-ID validation. A Pixel API 36 AVD opened an
`@hpke/core` wrap through that boundary in an Android **test-only** HPKE
composition and rejected altered `info`/AAD and a changed pinned key ID.
This proves the boundary can feed the draft operation in a virtual device; it
does not select a maintained HPKE receiver, prove supported-phone behavior or
authorize a sealed route. Q5 remains open.

## Q5 product device-floor decision (2026-09-23)

The founder selected **API 31+ for sealed-content mode only**. The existing M1 SMS gateway continues to support API 28+; a phone on API 28–30 must not enroll a sealed payload key, accept a sealed outbound grant, or claim sealed inbound protection. The decision does not authorize a software-key fallback on API 28–30. A future change to that device policy requires a new explicit decision and security review.

For API 31+, the draft's intended device payload private key is non-exportable through Android Keystore. The test-only proof does not establish a supported production decryptor or independently attest hardware protection.
