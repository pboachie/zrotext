# Authenticated customer routine service candidate

The service is available only when `CUSTOMER_ROUTINES_ENABLED` and `WORKFLOW_TOOLS_ENABLED` are explicitly enabled. Both default to false. Original-input policy, source-credential and execution requests additionally require `ORIGINAL_REPLY_READER_ENABLED`; disabling it refuses that slice before database access while preserving enabled owner-declared routines and lifecycle routes. A disabled routine mount exposes neither execution nor owner publication routes. This candidate admits deterministic or explicitly selected customer-local process routines; it does not activate a hosted model, provider account, phone renderer or automatically issue original-reader authority.

## Independent authority

A current owner configures an immutable routine policy using the owner session, CSRF token, exact origin and a separately authenticated input credential. The policy pins the input context revision and archive ciphertext digest, connector grant, kind, routine generation, explicit window, UTC-day call/unit limits and per-context turn limit. A context read credential alone cannot admit execution. Kind is one of FAQ, intake, note, reminder or owner reply; period is `utc_day`. Executor is `deterministic_local` or `local_process`. The deterministic policy has null/absent `adapter_id` and `artifact_digest`. A local-process policy requires both: a lowercase ASCII installation identifier starting with a letter (at most 64 characters), and a 64-character lowercase SHA-256 installation digest. Unsupported executors, model-selected executable paths and incomplete pairs refuse. The closed policy shape is `vectors/customer-routine-policy.schema.json`; runtime validation additionally checks resolved windows, ASCII timezone syntax, unequal opening/closing minutes and cross-field unit limits. The positive vector establishes syntax conformance, not current executable authority.

## Customer-local process trust boundary

The owner approves the adapter identity and installation digest through the authenticated policy service. A trusted local configuration maps that identifier to a fixed executable, working directory, arguments and artifact files. The digest commits the domain `ZT/customer-routine-local-executor/v1` followed by NUL and the ordered JSON tuple of identifier, canonical executable path, executable SHA-256, fixed arguments, canonical working directory and ordered artifact path/digest pairs. It is not a plaintext or provider-output commitment. Configuration possession does not create execution authority: the engine compares this identity with the independently returned current owner policy before exposing decrypted input.

The actual authenticated admission commits unknown execution and debits before the child can run. The engine obtains fresh current authority before invocation and after return; withdrawal, expiry, abort, timeout, malformed output and a lost admission response cannot automatically retry. The local process receives one bounded JSON line containing version one, exact call ID, kind and base64url input bytes; it receives no owner session, workflow credential, manifest private key or inherited environment. Its single bounded response contains version one, the same call ID and base64url output bytes. Child stderr and unexpected errors are redacted rather than returned to the caller. Accepted output still follows archive encryption and separate owner publication; a child cannot approve, select an output scope or dispatch.

This launcher is not a sandbox. The customer must protect the installation with platform permissions and trust the selected executable not to access ambient files/network or spawn detached descendants. Hash checks cannot eliminate privileged replacement between verification and spawn. Cancellation force-terminates only the exact direct child and observes exit within a bounded grace; it does not claim process-tree isolation or commercial usage settlement. Unknown outcomes keep their admission debits. Platform-specific isolation, real provider accounts and commercial prices remain separate decisions.

Build the locked TypeScript SDK before invoking `sdk/assistant/customer-routines.mjs`. Its `--config <private-config>` document contains an independently pinned manifest/root, the exact input scope, dedicated input credential, customer software reader key, encrypted-artifact store path and trusted local installation. `--identity explicit` reports the installation identity for owner review. `--configure explicit` submits the exact policy using an ephemeral owner session/CSRF document on private stdin; it does not manufacture approval from the configuration. `--execute <request-uuid>` uses actual authenticated current/admission. `--execute-original <request-uuid> <event-uuid>` uses the distinct original-input path described below. Keep the config and store under protected customer directories; configuration bytes, keys and credentials are not printed. This software-key entry point does not prove hardware or non-exportable key custody. It does not automatically run an owner publication ceremony or request a sending grant.

Integration requests use `POST /v1/workflow/routines`, JSON `{operation, params}` and a dedicated Bearer credential. Operations are `current`, `admit`, `admit_original`, `current_original`, `produced` and `resume`. Owner routes are `/v1/owner/workflow/routines/policy`, `/output`, `/withdraw` and `/export`. They require the current owner realm, not an integration credential pretending to be an owner. Credentials belong in trusted local configuration and authentication headers, never model parameters, JSON bodies or outputs.

The original `admit` operation still accepts only `owner_declared` direction; setting its direction to `inbound` refuses. Original messages use a separate operation and independent source credential. Metadata or role-3 context-content access cannot substitute for that source authority.

## Explicit original-input execution

An owner can configure `original_input: {grant_id}` on an immutable `local_process` policy. The exact grant is the separately issued original-reader grant, not a workflow context grant or an arbitrary connector identifier. Missing or null `original_input` preserves the owner-declared path. The current owner session, origin and CSRF remain required, alongside the current workflow input credential in `x-zrotext-routine-input` and the raw original-reader credential in `x-zrotext-original-reader`. The original credential does not confer permission to configure or execute a routine. Configuration possession, sender identity, webhook delivery and prompt text do not supply owner policy authority.

Original admission uses the workflow input Bearer credential and the separate raw `x-zrotext-original-reader` header. Its closed request is `{operation: "admit_original", params: {request_id, policy_id, context_id, input_revision, input_source_digest, event_id, accepted_manifest_version, event_envelope_digest}}`. `input_source_digest` binds the exact owner configuration context ciphertext. `event_envelope_digest` is SHA-256 of the exact retained original envelope bytes; the version identifies independently accepted manifest history. These are equality assertions checked against the server's retained verified provenance, not caller proofs. UUIDs, revisions, versions and lowercase 32-byte hexadecimal digests have the bounds in the service schema. Credentials, plaintext, reader points, verified booleans and `active_request_id` are not request fields.

The server joins actual current original-reader and workflow authority to the same account, connector, selected key, device, line, interval and peer; the workflow context and grant independently bind the contact, purpose, routine and generation. Current root/manifest, reader, owner/session, grant, context, event retention and expiry checks remain independent. The client verifies and decrypts the actual original envelope using the existing selected-reader SDK and independently pinned accepted manifest. It does not relabel that content as an owner-declared workflow context. First inbound FAQ, intake or other configured routine input does not need a preceding outbound request: explicit owner routine policy supplies execution authority. This is separate from #617's confirmation-consumption contract and does not classify the inbound message as confirming an action.

The admission transaction reuses the existing routine window, period, turn/unit limits and durable unknown checkpoint. An account/connector/event identity is retained for the account lifetime; a new request or policy cannot cause the same original event to execute again. Replay is status-only with `execute_once: false`, including after a lost response, restart or metadata pruning. `current_original` accepts only `{call_id}` and returns a non-executable current call after checking its retained original source and policy bindings. It is not a cached read permit.

The engine combines the decrypted owner configuration with the original message only inside the approved local process input. Current policy and source authority are checked outside the provider before and after asynchronous work; source revocation, event deletion, takeover, expiry or substitution refuses later checkpoints. Accepted output is sealed for the archive reader and awaits independent owner review/publication. Produced, bind and resume keep the original-reader header in addition to their existing input/output credentials. A fresh output Propose grant and authenticated exact-action approval are still required before downstream effects. The retained original-routine source also fences later approval and dispatch; it is not removed merely because an intermediate call or policy record is pruned.

The private CLI configuration adds `original_reader: {credential, scope}` only for a policy that explicitly selects original input. Its closed scope contains `account`, `device`, `line`, `interval`, `connector`, `readGrant`, `reader` and `peer`; byte fields use canonical base64url. The independently reviewed policy, manifest/root anchor, software reader key and installation remain in protected customer storage. The original credential stays in headers and private configuration, never provider input or printed metadata. The local process receives configuration and original message bytes, not either authentication credential. This software-key path makes no hardware/non-exportable key or OS sandbox claim.

`vectors/customer-routine-original-01.json` is a synthetic positive wire/parser fixture. Its schema tests reject authority fields and malformed correlation, but do not prove foreign-event refusal, current authority, budgets, cryptography or execution. Those require the real service and SDK integration regressions.

## Durable execution and budgets

The transaction commits an `unknown` call before returning `execute_once: true`. The authenticated request UUID is also the assigned output context UUID. Only the first successful admission response permits local execution. Exact replay returns `execute_once: false`; a lost response, timeout or process crash never permits regeneration. A different request body under the same UUID conflicts. Unknown calls consume their original units and turns; a local timeout is not proof that work did not occur.

Account UTC-day call/unit debits, per-context turns and admission tombstones are independent of call/policy metadata. New policies, withdrawal, content erasure and retention do not reset consumed budgets or reuse request identities. There are at most 1000 admission tombstones per account lifetime. A new UTC day resets the daily period allowance but does not reset this lifetime bound. Exhaustion refuses further admissions; there is no automatic eviction or replay-identity reuse. Full account erasure removes these account-bound records. These are logical routine limits, not financial credits or provider settlement.

## Encrypted output and owner publication

Before the produced checkpoint, existing reviewed ZTWC HPKE seals the output for the current archive reader. The checkpoint commits SHA-256 of these exact randomized ciphertext bytes. It never stores a plaintext digest. The assigned output context is a new context at revision one, with the unchanged input kind, account, device, line, interval and peer. The input context and exact input credential remain unchanged.

The owner separately reviews and publishes those exact archive bytes using the existing binary owner context service. The owner creates a distinct encrypted role-3 projection and uses the current owner password/MFA ceremony at `/v1/auth/workflow-grants` to issue a fresh exact output grant. The server verifies current reader and scope authority but cannot prove that independently randomized archive and projection ciphertexts represent identical plaintext; that relationship is explicitly declared by the owner.

Binding and resume require both independently current input and output scopes. The output credential must permit both content and proposal operations; it cannot widen or replace the input credential. Cross-account, connector, reader, line, contact, purpose, interval, revision or digest substitutions refuse. Fresh output routine generation is independently checked, rather than copied from the input generation. Resume registers only a sensitive proposal under the existing exact-action ledger. It creates no approval, message or delivery attempt. Owner approval, exact message binding and downstream effect authority remain separate.

## Privacy and lifecycle

No routine plaintext, model input, private key or credential is persisted in the server call ledger. Export is current-owner authenticated and paginated by an explicit metadata section. Context/contact erasure and bounded retention remove call/policy metadata while preserving the minimum consumed-budget and replay records until account erasure. Original-event deletion invalidates source authority and fences derived effects; minimal immutable original admission/source tombstones survive metadata and ciphertext pruning until full account erasure. These tombstones contain identifiers and ciphertext commitments, not original plaintext, and are included in the authenticated lifecycle boundary. Customer-local artifacts remain encrypted; byte-buffer clearing is best effort and cannot promise erasure of JavaScript strings, engine copies, storage pages or backups.

Withdrawal stops admission and resume and irreversibly fences every separately published output routine linked to that policy. Existing owner takeover or stopping the input routine propagates through exact published-output links, including chains and cycles, before later output approval or preparation can proceed. Unbound call identities cannot stop unrelated routines. Erasure and retention stop linked outputs before deleting their association; they do not refund unknown work or renew authority.

Synthetic HTTPS fixtures establish client transport behavior only. The separate real-router/disposable-database fixture covers service authority and actual reviewed client crypto. Neither proves deployment activation, physical-device operation, carrier delivery or approval of an unresolved provider or reader policy.

The multi-process fixture uses serialized, exportable synthetic customer keys and an explicitly owner-configured ten-second execution policy. It does not prove hardware or non-exportable key custody. Existing deadline and unknown-outcome refusal tests retain their separate bounded policies.
