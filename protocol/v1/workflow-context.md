# Encrypted workflow context candidate

ZTWC01 is a proposed, implemented library/API candidate for owner-entered jobs,
appointments and general context. Its router is not mounted by `main`. It neither
enables conversation capture nor sends SMS, schedules jobs, calls calendars/CRM,
charges payments or authorizes an agent. It extends an existing approved
`conversation_intervals` identity; it does not create another conversation store.

Only details encrypted in the customer client are stored. The server has no
private reader key, decryption, plaintext search, reply classifier or hidden
integration reader. Type 1 means job, 2 appointment and 3 general context. These
types and lifecycle metadata are public; names, times and other details stay
inside ciphertext. An authenticated malicious owner can submit arbitrary opaque
bytes; server framing validation is not proof of successful encryption or meaning.

## Client encryption and exact binding

The TypeScript candidate uses the existing HPKE library with DHKEM(P-256,
HKDF-SHA256), HKDF-SHA256 and AES-128-GCM. Each revision uses a fresh encapsulation
generated by the library. Only the just-verified manifest's active role-2 archive
reader with inbound-read scope can receive it, with an active role-4 signer for
the selected device/line establishing current conversation authority. This is
independent of the Android/SMS payload profile and conveys no radio permission.

Canonical authenticated header, in order, with no optional fields:

| Field | Encoding |
|---|---|
| Magic/version/type | `ZTWC`, byte 1, type byte 1..3 |
| Account/device/line/interval/context | Five nonzero UUIDs, 16 network-order bytes each |
| Binding generation/revision/expiry/trust generation/manifest version | Five positive signed-range 64-bit big-endian integers |
| Peer digest | SHA-256 of exact approved statement peer bytes, 32 bytes |
| Archive reader key ID | Existing manifest role-2 key ID, 32 bytes |
| Current manifest semantic digest | 32 bytes |

The header is exactly 222 bytes and is the HPKE AEAD AAD. HPKE info is the ASCII
domain `ZT/workflow-context/hpke/v1` followed by NUL and that exact header. Append
the 65-byte uncompressed P-256 encapsulation, a four-byte big-endian ciphertext
length and ciphertext including its 16-byte tag. Plaintext is 1..32768 bytes;
the whole envelope is 308..33075 bytes. Clients capture mutable input before the
first asynchronous operation and check the exact expected header before opening.

Current root pin, manifest, reader, owner role/session, line approval and exact
interval binding are required before writes/reads and again after lock waits.
Writes require an active interval and its originating owner session to remain
authorized at both write fences; retained reads also permit history. Withdrawn
or expired intervals, stale manifests, changed peers/readers or revoked access
fail closed. An owner can refresh a context revision under a newer manifest that
retains the same reader and trust generation. Historical version reads require
their exact manifest still to be current. Opaque owner takeout can retain older
ciphertext without conferring current reader or decryption authority.

## Dormant owner API

The independently unmounted router requires an owner session; bearer credentials
are refused. Mutations use the existing same-origin/CSRF owner mutation extractor.
Every response, including errors, is no-store and nosniff.

- `POST /v1/owner/workflow/contexts`: binary envelope with content type
  `application/vnd.zrotext.workflow-context.v1`, UUID `Idempotency-Key` and
  canonical decimal `X-Zrotext-Context-Revision` expected head (0 for creation).
  Envelope revision must equal expected head + 1. Exact retries return the same
  revision; changed bytes, reused request IDs and stale concurrent heads conflict.
- `GET /v1/owner/workflow/contexts/{id}?revision=N`: exact ciphertext for the head
  or selected retained revision; no decrypted or inferred fields.
- `POST /v1/owner/workflow/exceptions`: context ID/revision, source kind/ID and
  reason. No message body, freeform explanation or inferred approval is accepted.
- `GET /v1/owner/workflow/contexts/{id}/exceptions?before=UUID`: 20 scoped metadata
  rows and an optional next cursor. Foreign context/cursor identities are refused.
- `POST /v1/owner/workflow/exceptions/{id}/resolve`: UUID request ID and expected
  exception revision 1. Transition to resolved revision 2 is irreversible; an
  exact retry succeeds without another audit record.

Source kind 1 is a verified inbound event with original provenance for the exact
interval/device/line/binding. Reasons 1 (ambiguous reply) and 5 (approval mismatch)
are explicit client declarations, not server conclusions about plaintext. They
never grant approval. Kind 2 is an existing sealed outbound message whose account,
device, line, generation and retained peer match; reason 2 requires state unknown,
3 expired, and 4 cancelled. Purged peers cannot be guessed. Unknown sealed work
requires the separately reviewed grant/runtime lifecycle; this candidate does not
weaken the existing transport effect guard to manufacture it.

Exception identity is the first 16 bytes of SHA-256 over
`ZT/workflow-exception/id/v1` + NUL, account/context/source UUID bytes and source
kind/reason as signed 16-bit big-endian integers, with UUID version 8/variant bits
set. It excludes revision so event replay cannot duplicate an exception. A
different original revision under the same identity conflicts; resolution does
not make the source replay create another pending row.

## Bounds, retention and takeout

Each account has at most 1000 context identities, 8 MiB retained envelopes and
8192 metadata audit records; each context has at most 128 immutable revisions
and 32 exceptions. Context expiry is at most 30 days ahead of database time.
Account locking serializes budget reservation, source creation and concurrent CAS.
New context/version/audit rows commit together; a deferred head foreign key
prevents a head without its immutable version.

The existing retention worker purges ciphertext on expiry or withdrawal, keeping
request digests as replay tombstones. A later bounded pass removes context,
versions, exceptions and audit after the sealed-inbound retention interval.
Purged bytes cannot be rewritten or rehydrated. Interval cleanup erases the closed
interval's peer-bearing statement at the
existing sealed-content retention cutoff, while retaining identity for its
dependent contexts. The resulting withdrawn phase also schedules context
ciphertext purge; no foreign key or content-retention window is bypassed.

Owner export includes independent 20-row pages for all four introduced tables:
`workflow_contexts_before`, `workflow_versions_before`, `workflow_exceptions_before`
and `workflow_audit_before`, with corresponding next cursors. Version envelopes
use `envelope_hex`, null after purge. The maximum ciphertext export page is bounded
by 20 envelopes. Existing schema-protected trust history can still block whole
account erasure; when erasure is authorized, all four tables appear in the
existing FK-safe deletion plan before conversation intervals. No deletion of
trust tombstones or replacement of existing erasure gates is introduced.
