# M1 local SMS adapter slice

This build retains the M0 heartbeat-only gateway session. The UI and WSS probe never call `SmsAttemptAdapter`; there is no server execution grant, inbound SMS path, or test-send screen. Installing the APK does not send an SMS.

`SmsAttemptAdapter.submit` is an internal boundary for a future grant-validated dispatcher. It requires a stable UUID attempt ID and an explicit active subscription ID. It validates `SEND_SMS` and `READ_PHONE_STATE`, the selected subscription, an E.164 destination, and a body of at most six segments before reserving the attempt. The Room transaction writes `submitting` and one row per segment before `SmsManager` is called. The callback receiver stores each sent and delivery result code once. Neither the recipient nor message body is stored in Room.

On process start, unresolved `submitting` rows become `unknown`. A synchronous exception after reservation is also `unknown`. A repeated attempt ID is refused, including after a restart. Sent callbacks may resolve an unknown attempt; no callback and no returned call alone proves submission. `submitted` requires every segment's sent callback to succeed. `delivered` requires every delivery status report to parse as received; an unparseable report does not prove delivery. Mixed sent outcomes become `partial_failure`. Missing or unverified delivery receipts become `delivery_unknown` after 24 hours when the process next starts. There is no automatic radio retry or failover.

This is local state only. Durable server event reconciliation, execution grant validation, pacing, cancellation/expiry, inbound reply handling, and real-phone carrier results remain M1 integration and hardware work. A controlled send must use a dedicated test phone, a recipient controlled by the operator, and an explicit grant/test setup. Debug APK compilation and local unit tests do not satisfy that gate.

## Enrollment client slice

The phone can manually claim a one-use pairing from an HTTPS server origin, pairing UUID, and token entered on the screen. It creates a versioned non-exportable P-256 signing key in Android Keystore, prefers StrongBox when the device advertises it, and reports the actual key security level. A creation-time StrongBox fallback is shown only when known; reopening a stored key does not claim to know its creation history. The app submits its X.509 SPKI DER public key as base64url without padding, checks the returned SEC1-point fingerprint, signs the exact server enrollment challenge with `SHA256withECDSA`, and shows the comparison code and fingerprint for owner approval in the browser. The pairing token is not written to app preferences or a URL.

The UI cannot create or approve the owner-side pairing, learn an approved device ID, or dispatch SMS. Those integrations require owner authentication and server deployment. A failed claim or proof is not retried automatically because the token and challenge are one-use. The manual HTTPS origin must be chosen from a trusted server; a production QR/bootstrap format and origin pinning remain to be specified.

## Authenticated heartbeat client slice

The separate authenticated service accepts a manually entered approved device UUID and a `wss://` URL ending in `/v1/device-stream`. It sends `hello`, signs the server's one-use challenge with the Keystore identity, then sends heartbeats only after the server returns a session epoch. It bounds frame size, rejects unexpected fields and stale acknowledgment epochs, and stops on handshake or heartbeat timeout. JVM state-machine tests cover out-of-order frames and stale epochs. This client cannot learn its approved UUID from pairing yet; the owner must provide it for the test. No live authenticated WSS session, screen-off run, automatic reconnect, grant handling, or SMS path has been verified.
